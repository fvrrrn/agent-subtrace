# Loss до full fine-tune: SED, MIL и аномальные подпоследовательности

Дата: 18 октября 2026. Статус: ограниченный обзор первоисточников и выполненная
CPU-диагностика синтетических выходов. Обучений и оценок моделей здесь нет.
Предложения ниже требуют интеграции основным агентом в новый протокол.

## Короткое решение

Рекомендуются **три условия**, а не новая сетка скалярных pooling:

1. **A — прежний broad + общий endpoint**, контроль.
2. **B — отдельная token-голова прогноза метки действия + evidence auto-pool**.
3. **C — та же token-голова + обучаемая классификация признаков подпоследовательностей**.

Приоритет содержательной гипотезы — C: решение получает признаки и конечное
каузальное состояние, а не только одномерную кривую. B — дешёвая проверка
разделения задач, с явным риском неучёта позднего исправления. A нужен на тех же
новых данных и backbone. Во всех условиях одновременно token-loss и event-loss,
Mamba + классификационные головы, без добавленного attention.

**Важное ограничение сравнения:** A→B меняет и token-target, и разделение голов,
и event-readout. Это сравнение трёх систем при согласованном бюджете, не факторный
эксперимент, доказывающий эффект одного loss. B→C сохраняет token-target и
сравнивает два event-readout. Три условия не позволяют одновременно изолировать
все три фактора; не приписывать улучшение одному из них.

## 3. Семантика: три разных объекта

Пусть `h_i` — состояние causal Mamba после токена i текущего действия, с полной
доступной историей; `Y` — метка завершённого candidate action **до его результата**.

* `P(Y=1 | history, action[:i])` — прогноз конечной метки этого действия.
* Риск исполнения уже прочитанного частичного действия — другая задача.
* Локальное свидетельство нарушения — третья задача, не идентифицируемая по Y.

Общий префикс безопасного и опасного продолжения должен иметь одинаковый
каузальный выход. Обучение прогноза Y на таких примерах оптимизирует условную
частоту продолжений, а не требует знать будущее. Это допустимое supervised
forecasting: будущая метка присутствует только в loss, но не во входе.

Напротив, утверждение «полное действие safe, значит каждый префикс безопасен»
не следует из метки. Опасный замысел может быть отвергнут позже; цитата атаки
может закончиться отказом. Смена порядка с тем же набором scalar scores
неразличима для симметричного MIL pooling, но может менять смысл действия.

**Предлагаемая замена broad в B/C:** token BCE с target Y на каждом токене
интерпретируется строго как прогноз конечной метки, не token-risk gold и не
evidence localization. Это не предположение безопасности всех префиксов.
Такая цель не требует неизвестного онлайн N; ранняя неопределённость законна.
Она всё ещё может доминировать над редкими поздними свидетельствами и учить
source shortcuts. Поэтому это проверяемая альтернатива, не найденная истина.

Если пользователь требует именно локальный token-risk, action-labels для этой
интерпретации недостаточны. Нельзя переименовать forecasting в risk. Аудит
StepGuard ещё должен установить наличие реальных токеновых/span меток и их
причинную семантику. Rationale разметчика не вводится в модель и сам по себе
не является валидной token-разметкой. Не менять B/C на rationale targets
молча после просмотра результатов.

## 4. Ровно три предлагаемых условия

Общее: один forward целого диалога, состояние не сбрасывается между действиями;
pooling только внутри current action. Tool result текущего действия и будущие
сообщения исключены причинной сериализацией. История не обрезается окнами readout:
каждое `h_i` уже зависит от полного допустимого прошлого.

Для диалога с K размеченными действиями:

```
L_dialog = (1/K) Σ_a [L_token(a) + 0.1 L_event(a)]
L_token(a) = (1/N_a) Σ_{i in action_a} BCEWithLogits(t_i, target_i)
L_event(a) = BCEWithLogits(z_a, Y_a)
```

Unlabelled context и padding не участвуют в loss; неодинаковая длина действий
не меняет их суммарный вес напрямую. Диалоги с разным K сохраняют прежнюю
нормировку: это не event-uniform выборка. Не добавлять class weights или focal
loss одновременно. Общие init Mamba, seed, порядок диалогов, optimizer,
число обновлений, данные и backbone фиксируются до просмотра dev.

### A. Shared broad + endpoint — точный контроль

```
t_i = w_t^T h_i + b_t
target_i = Y * g(i/N), g(u) = (0.9 + 1.2u - 1.5u²)/1.14
z_a = t_N
```

Broad — искусственная вспомогательная форма, не вероятность и не token gold.
В частности, g(1)=.5263158 конфликтует с hard event target 1. Контроль намеренно
сохраняет это свойство; ранние значения используют N только в training target,
не в признаках модели. Новая версия данных требует нового matched контроля.

### B. Раздельные forecast/evidence головы + auto-pool

```
t_i = w_t^T h_i + b_t; target_i = Y
r_i = w_e^T h_i + b_e; p_i = sigmoid(r_i)
alpha = softplus(a), initial alpha = 1
w_i = exp(alpha*p_i) / Σ_valid exp(alpha*p_j)
s_a = Σ_valid w_i*p_i
z_a = logit(s_a)
```

`L_token` обучает только forecast-выход, event-loss — evidence-выход; оба
обучают общую Mamba. Разделение устраняет прямую конкуренцию за один scalar,
но не гарантирует согласия градиентов общих параметров. `p_i` — latent activation,
не калиброванный risk. Auto-pool — один глобальный обучаемый scalar, не Q/K/V,
не новый attention-блок, не learned token-weight network. Если запрет пользователя
охватывает вообще любые softmax-веса, B требует уточнения до интеграции.

Выбрано alpha>=0 для evidence-presence семантики; отрицательная ветвь min-pool
из оригинальной статьи здесь не нужна. Не добавлять подбор alpha/regularizer.
Для численной устойчивости реализация должна вычислять log(s) и log(1-s)
через logsumexp(log w + logsigmoid(±r)), не отсекать значения clamp-ом.

Существенный риск B: раннее свидетельство остаётся в bag после безопасного
исправления. Модель может научиться не активироваться до однозначного нарушения,
но pooling сам не умеет отзывать прошлое. Поэтому B не рекомендован как
единственная финальная гипотеза; его достоинство — чистое отделение forecast
от latent evidence и крайне малый дополнительный расход.

### C. Признаки подпоследовательностей + endpoint-conditioned classifier

Token-цель и token-голова **точно как в B**. Для заранее фиксированных ширин
`W={8,32,128}` и каждого правого конца i внутри current action:

```
l = max(action_start, i-w+1)
v_{i,w} = concat(mean(h_l...h_i), h_i-h_l, h_i)
f_{i,w} = ReLU(A v_{i,w} + b), output dimension 32
m_w = coordinatewise_max_i f_{i,w}
z_a = u^T concat(h_N, m_8, m_32, m_128) + c
```

Один общий A для всех масштабов; никакого дерева, attention, дополнительной
рекуррентной модели или generative decoder. Это небольшой nonlinear classifier
внутри головы. При d=256: A содержит 24 576 весов + 32 bias; event-выход —
352 веса + bias. Это больше B (257 evidence параметров + alpha), следовательно
сравнение не является parameter-matched. Числа параметров раскрывать.

**Почему это не прежний неудачный multiscale scan:** сначала извлекается
нелинейный 32-мерный признак из векторных состояний и их изменения, потом
выполняется pooling. `mean(w^T h)` равен `w^T mean(h)` и сам по себе ничего
не добавляет; ReLU до pooling и endpoint-канал делают C нетривиальным.
Компонентный max может собрать признаки из разных интервалов: это допустимо
для классификации композиции, но не доказывает существование единого witness.
`h_i-h_l` — признак изменения представления, не причинный эффект интервала.

Конечное h_N позволяет вычитать свидетельство при отказе/уточнении через
обучаемые отрицательные коэффициенты. Это возможность представления, не
гарантия, что модель ей воспользуется. В событие входит только уже прочитанный
candidate; для раннего онлайн-выхода m_w можно строить лишь по правым концам <=i.
Не выдавать финальное m_w за ранний каузальный token-output.

Частичные окна в начале нормируются по фактической длине; padding полностью
исключён, а не представлен нулевыми состояниями. Средние через prefix sums,
без unfold тензора N×128×d. Рабочая сложность линейна по N при трёх масштабах;
активации N×3×32 и стоимость shared MLP измеряются gate, а не считаются бесплатными.

## 5. Градиенты, конфликт и эффективные веса

Для token BCE: `dL_token/dt_i = (sigmoid(t_i)-target_i)/N`.
Для endpoint BCE: `dL_event/dt_N = sigmoid(t_N)-Y`.
На positive endpoint с общим scalar и независимыми выходными координатами
стационарная точка A равна:

```
p_N* = [g(1) + 0.1*N] / [1 + 0.1*N]
```

Для N=16/256/4096: .817814 / .982192 / .998846. Это локальная алгебра loss,
не предсказание обученной Mamba. Она показывает: коэффициент .1 не означает
«event в десять раз слабее» на endpoint; его локальный вес относительно
одного token слагаемого растёт как .1N.

Linear-softmax `s=Σp²/Σp`:

```
ds/dp_i = (2p_i-s)/Σp
dL_event/dr_i = [(s-Y)/(s(1-s))] * ds/dp_i * p_i(1-p_i)
```

На positive bag слабый p_i<s/2 подавляется, хотя broad почти повсюду требует
роста. В safe bag слабые значения иногда временно повышаются. Это особенность
производной, не ошибка реализации и не доказательство вреда параметрам.

Auto-pool:

```
ds/dp_i = w_i * [1 + alpha*(p_i-s)]
ds/dalpha = Σw_i (p_i-s)²
```

Alpha обучается увеличиваться на positive и уменьшаться на negative bags
(если variance>0, без учёта остальных примеров). Большой alpha тоже может
делать координатную производную отрицательной. При постоянном p параметр
alpha не получает градиента; auto-pool не создаёт свидетельство из ничего.

Раздельные головы не позволяют вычислять содержательный cosine между их
несовпадающими output координатами. Нужно сравнивать `∇_theta L_token` и
`∇_theta (0.1 L_event)` на **одних и тех же общих параметрах** или h_i:
norm ratio, cosine и разбивку по Y/N/source. У C дополнительно видно, идёт ли
event-градиент через окна, а не исключительно endpoint. Это малый заранее
фиксированный train-only gate, не новая адаптивная сетка весов.

При постоянных сходных остатках token-output L2 норма убывает как 1/sqrt(N);
endpoint gradient имеет O(1), поэтому отношение может расти как sqrt(N).
У mean-like pooling каждый token event gradient имеет O(1/N). Эти оценки
не заменяют Jacobian backbone/Mamba и измерения общих параметров.

## 6. Выполненная CPU-диагностика

Команда: `python3 graph-safety/scripts/analyze_sound_anomaly_losses.py`.
Только стандартная библиотека Python, float64 числа, аналитические производные;
ни загрузки модели, ни GPU, ни установки зависимостей. Synthetic short spike:
один .9 среди .05; long signal: 128 значений .8 среди 128 значений .05;
safe correction: восемь .8, затем восемь .05 с Y=0. Это сконструированные
сценарии scalar readout, а не метки текста или validation gains.

| Сценарий | Endpoint | Linear MIL | Auto-pool alpha=1 | Auto-pool alpha=8 |
|---|---:|---:|---:|---:|
| Короткий spike, N=16 | .050000 | .513636 | .164691 | .886033 |
| Тот же spike, N=256 | .050000 | .106044 | .057728 | .711987 |

Alpha=1/8 здесь заданные аналитические точки, не предлагаемые training arms.
При alpha=1 для одного высокого p максимум его веса <=e/(e+N-1);
фиксированный alpha в общем случае не устраняет разбавление на больших N.
Нормировка по N устраняет рост на постоянном фоне, но не length shift при
фиксированном числе signal токенов. Полное дублирование bag сохраняет все
показанные скоры; это не равнозначно добавлению новых фоновых токенов.

240 добавленных padding значений .999 после **маскирования** дали точную
разницу score 0 для endpoint/MIL/auto-pool. Реальный фон .05 остаётся валидным

## 7. Normal background, energy и NULL

Теоретически posterior log-odds можно записать как условный likelihood ratio:

```
logit P(Y=1|v,c) = log p(v|Y=1,c) - log p(v|Y=0,c) + log prior_odds(c)
```

Это тождество при корректных плотностях; наш classifier не оценивает такие
плотности автоматически. Редкое безопасное действие может иметь низкий normal
likelihood, а типовой harmful шаблон — высокий. Источник/роль/длина влияют на
фон; глобальная Gaussian-норма по hidden states с их корреляциями не решает это.
Новый density model сейчас увеличит объём работы без подтверждённой выгоды.

Дискриминативная energy difference `z=E_safe(v)-E_unsafe(v)` с BCE — допустима,
но для двух linear energies это **алгебраически одна linear голова**, не новый
метод. Общий сдвиг energies неидентифицируем. То же относится к простому
переименованию прежнего `logmeanexp(r)-NULL(h_N)`: новый термин не исправляет
провал NULL. В C endpoint-conditioned итоговый classifier может учить разницу
свидетельства и разрешающего контекста без дополнительной NULL-ветви.

Калибровка разницы offset/temperature не восстанавливает плохое ранжирование;
положительная temperature сохраняет ranking. Любая калибровка только на
разрешённом dev и после фиксации модели; benchmarks и confirm не используются.
В данном ограниченном screen калибровка не добавляется. Evidence rank и
raw-risk probability не отождествляются.

* Порядок при ограниченном времени: A и C; B только если помещается вместе с
  финальным этапом. Это не разрешение молча урезать входы, эпохи или сравнивать

  бюджет нужны на обоих; не выбирать стратегию по разным незавершённым screens.
* Стоимость оценивать по измеренному head-step и числу диалогов, с запасом
  25% и сохранением резерва финальных оценок. Не запускать новый arm, если
  его completion + fullFT 1 epoch + оценка/сохранение не помещаются в дедлайн.
* Основной критерий прежний: source-held-out dev-select AP; ties event BCE,
  затем затраты. Также отчёт PR-AUC (трапецеидальная), ROC-AUC, P/R/F1/Accuracy,
  FP/FN и количество общих полностью оценённых действий. Низкий recall при .5
  не скрывать. Это адаптивно просмотренный dev, не held-out confirmation.
* Только после выбора loss и backbone продолжить с выбранного head checkpoint:
  full fine-tune backbone + Mamba + head ровно **1 эпоха**, без LoRA и без
  сброса head. Меньший backbone LR, новый optimizer зафиксировать заранее.

Главный вывод: статьи мотивируют разделение прогноза метки, локального
свидетельства и event-классификации. Они не дают оснований считать broad
token-curve истинной разметкой или любую scalar MIL формулу оптимальной.
Самая содержательная ограниченная проверка — обучить классификатор доступных
признаков подпоследовательностей с конечным контекстом и одновременно сохранить
честно названный token-level прогноз, затем измерить перенос на dev-select.
